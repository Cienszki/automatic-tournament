# WP-06: the hosting trial, local part

Written on 2026-11-23 by Opus, on branch `wp/06-hosting-trial`. The owner has not yet switched on staging or allowed a deployment, so this is the half of WP-06 that runs on this machine: the helpers that M1 keeps (`src/platform/cache`, the forwarding rule), one server-rendered teams page on PostgreSQL, and the measuring scripts. Everything was measured against a local production build (`next start`) with the four imported tournaments in a local PGlite database. **The local numbers prove that the scripts work and that the page is cacheable; they are not the trial's result.** The trial's numbers come from a Vercel preview against the staging database, with the steps in "What remains" below.

The short version:

- `/<slug>/teams` of a tournament in the new database is rendered on the server from three cached statements, with the theme as CSS variables in the HTML and the team list in the first response. It is static per tournament (`Cache-Control: s-maxage=31536000`, `x-nextjs-cache: HIT` from the second request), and so is its client-navigation payload. An invalidation makes the next request render fresh data: locally about 40 ms after the call.
- Tournaments on the old site, the pages not moved yet, the old `/api/` routes and the old site's `/_next/` files are forwarded to the old site's address. Nothing changes unless `PLATFORM_ROUTING=on`.
- The middleware knows which slugs are new without asking the database, because it is given the short list of slugs that are still on the old site. Why that is enough is the next section but one.
- Three things found on the way matter for M1: under `next start`, a middleware rewrite inside the app makes a page uncacheable and, next to config rewrites, does not reach it at all (so the moved pages and the `.rsc` strip are rewrites in `next.config.mjs`); an unknown slug answers 200 with the not-found page because of the root loading screen; and the root layout still sends 44 kB of translations and a Firestore-reading provider with every page (the last two are WP-08's).

### The cache helpers (ADR-02, ADR-12)

`cachedQuery(fn, { name, tags, revalidate? })` wraps a read in Next's data cache (`unstable_cache`). The key is the query's name and its arguments; the tags come from `tags.ts`, the only place a tag is spelled: `t:<tournamentId>` for everything of a tournament, `t:<tournamentId>:<kind>` for the kinds of ADR-12 (`core`, `teams`, `matches`, `standings`, `bracket`, `content`, `stats`, `fantasy`), and `slug:<slug>` for the slug lookup. Every tournament query carries the tournament-wide tag too, so one invalidation refreshes a whole tournament (after an import, or a theme change). `invalidate(tags)` is what a command or job will call.

Two traps are closed in the helper. The data cache stores JSON, so a `Date` from the database would come back as a string on a hit and as a `Date` on the miss that filled it; a result that is not plain JSON is refused on the miss, every time. And Next keys an entry by the callback's source text plus the key parts; every callback made by the helper has the same source, so the name is part of the key. Pages that use these queries become static: Next attaches the queries' tags to the page, so an invalidation also drops the cached page and, on Vercel, the CDN copy.

### The page

`/platform/<slug>/teams` is the internal address; visitors use `/<slug>/teams`, and the internal one answers 404 from outside. It lives outside `src/app/[tournamentSlug]/` because that folder's layout is the old client layout with the loading screen and the Firestore reads; WP-08 turns that layout into a server component, and the page then moves into it. The page is `force-static` with an empty `generateStaticParams`: nothing is rendered at build time (a build reads no database, and `build-offline.mjs` still passes), each tournament is rendered on its first request and then served from the cache until a tag of its data is invalidated. `force-static` also stops the root layout's language cookie from making the page per-visitor; the language stays Polish until WP-08 takes it from the tournament. The slug `platform` is reserved (`src/lib/reserved-slugs.ts` and the copy in `firestore.rules`).

The team list is three statements whatever the number of teams (teams, current roster rows, group memberships with their stage), run in parallel, and assembled by `buildTeamList`: teams by group of the earliest stage, then name; players by position, then substitutes, then coaches; every team listed with its status, as on the old page. A database test asserts the three statements on an 18-team and an 8-team tournament.

### The forwarding rule (ADR-15)

Three variables, read by the middleware at run time and by `next.config.mjs` at build time (so a change needs a new deployment, which is true on Vercel for middleware variables anyway):

| Variable | Meaning |
|---|---|
| `PLATFORM_ROUTING` | `on` switches the rule on. Anything else: the middleware and the config behave exactly as before (the 410 on `/api/admin`, the `.rsc` strip, nothing else) |
| `LEGACY_ORIGIN` | the old site's address. Unset: nothing is forwarded, and what the platform does not serve falls to the old pages that are still in this app (local runs) |
| `LEGACY_SLUGS` | comma-separated slugs still served by the old site; forwarded whole, even when they are also in the new database (a mirror) |

With the rule on, for each request:

1. `/api/admin*`: 410, as before.
2. `/platform/*` from outside: 404.
3. `/api/platform/*` and `/prototype/*`: served here.
4. Any other `/api/*`: forwarded (the old site's routes; old pages loaded through the new app call them).
5. `/<slug>/<moved page>` with a slug that is not on `LEGACY_SLUGS`: served by the new platform. `next.config.mjs` has a `beforeFiles` rewrite to `/platform/<slug>/<page>` that excludes the old-site slugs and `api`, `platform`, `prototype`, `_next`, with and without the `.rsc` suffix that client navigations carry when they come through the community site; another `beforeFiles` rewrite strips that suffix from every other path.
6. Everything else (old-site tournaments, pages not moved yet, the home page, `/creator`): forwarded.
7. The old site's `/_next/` files: this build does not have them, so a `fallback` rewrite to `LEGACY_ORIGIN` serves them. `fallback` runs after every page, file and dynamic route, exactly like the community site's rule in front of us today. The middleware skips static files entirely (its matcher), so they cost no middleware call.

Each response says which way it went in `x-platform-route` (`platform`, `forward`, `serve`, `not-found`), only when the rule is on. A forward keeps the path and the query; a client navigation is forwarded without its `.rsc` suffix and with its `RSC` header, as the old site expects. With the rule on, the middleware rewrites nothing inside the app; it only answers (410, 404) or forwards.

**Why the moved pages are rewritten by the config and not by the middleware.** Measured, not assumed, over several builds:

1. Under `next start`, a page reached through a middleware rewrite is rendered per request with `Cache-Control: private, no-cache, no-store`, because the route module re-reads the original URL and re-applies only the config's rewrites before it decides whether the page is static (`next/dist/build/templates/app-page.js`, `routeModule.match(pathname)`). Reached through a config rewrite, the same page is static (`x-nextjs-cache: MISS`, then `HIT`).
2. Once the config has `beforeFiles` rewrites, a middleware rewrite inside the app (the `.rsc` strip, to the moved page or to any other path) no longer reaches a page at all under `next start`: the request falls through to the `fallback` rewrite with its original path, so a client navigation through the community site was forwarded to the old site. Stripping the suffix with a config rewrite instead fixed it (the navigation payload through the front proxy: `x-nextjs-cache: HIT`).

On Vercel the router hands the function the rewritten path, so a middleware rewrite is expected to work there too, but the config rewrites work everywhere, including the fallback hosts of ADR-03. With the rule off none of this applies and the middleware strips `.rsc` itself, as before. A related fact about today: on the old site's own hosting, a client navigation that came through the community site and was rewritten by the middleware is never served from a cache.

### How the middleware knows which slugs are new

The WP says "a slug that is not in the new database is forwarded". Asking the database on every request is ruled out (latency at the edge, a database call per page view even for CDN hits). The options considered:

| Option | Cost per request | Staleness | Verdict |
|---|---|---|---|
| Query the database in the middleware | one round trip, at the edge | none | ruled out by the WP |
| The list of new slugs in an environment variable | none | a deployment per new tournament | fails at go-live step three, when organizers create tournaments themselves |
| Vercel Edge Config holding the new slugs | a read per request (counted; the free plan's allowance is far below 1,000,000 a month) | seconds | vendor-specific and metered on the free plan |
| The middleware fetches a cached list of new slugs from the app itself and keeps it in memory for a minute | none on a warm instance; a fetch per cold edge instance, which is a CDN request and a function call | up to a minute | adds CDN requests, and on a protected preview the fetch needs a bypass secret |
| **The list of old-site slugs in an environment variable (chosen)** | none | a deployment per go-live step | see below |

The choice rests on ADR-15: the old site is frozen for features, every new season is created on the new platform, and the old site's tournaments leave it one go-live step at a time. So the set the middleware must know is the old site's, not the new platform's: today `pdl`, `pdl-s2`, `wiosenna`, `letnia`, and it only ever shrinks. Every tournament created on the new platform is served without any change to the setting, and each go-live step, which is a deliberate change with its own checks, removes one slug from the list in the same deployment. The middleware stays a few lines of string work with no network call (the edge bundle went from 114 to 115 kB; the rest is Sentry's edge SDK, WP-04's note).

What it does not do, and the cost of that: a slug that is in neither system is rendered by the new platform, whose page answers "not found", instead of being forwarded so that the old site answers "not found". A visitor sees the same thing. A tournament created on the old site after this setting was written would be missing from the list and would get the new platform's "not found" until it is added. The owner creates the old site's tournaments, so the rule for the go-live packages is: no new tournament on the old site, or add its slug to `LEGACY_SLUGS` the same day. If that ever becomes too fragile, the fallback is the cached-list option above; `decideRoute` takes the set as data, so only `readRoutingConfig` would change.

The tests: `src/platform/routing/decide.test.ts` (every decision above, the settings, and the config rewrites run through Next's own matcher with `unstable_getResponseFromNextConfig`, including that `pdl` on the list does not catch `pdl-s2`), `src/middleware.test.ts` (the old behaviour with the rule off, recorded before the change; the rule on; the matcher).

## Found on the way

1. **Middleware rewrites inside the app do not work with static pages under `next start`** (above). The moved pages and the `.rsc` strip are config rewrites; with the rule on, the middleware only answers or forwards. To check on Vercel: that the same config rewrites give `x-vercel-cache: HIT` (step 5 below).
2. **An unknown slug answers 200 with the not-found page** (and `noindex`), not 404, for browsers and crawlers alike (checked with a Googlebot user agent): the root `src/app/loading.tsx` puts every page inside a Suspense boundary, so the status is sent before the page can call `notFound()`, and `notFound()` in `generateMetadata` does not help because the metadata streams too. The response is cached like any page and dropped with the slug's tag. WP-08 removes the root loading screen, which is the fix.
3. **The root layout is heavy for every page.** Its `NextIntlClientProvider` carries all of `messages/pl.json` (44 kB) into each page's HTML and navigation payload, which is most of the 70 kB payload of a 12-team page; and its client providers start the Firestore SDK. Both are WP-08's (language from the tournament, providers seeded from the server).
4. **Next's data cache keys by the callback's source text.** Handled in `cachedQuery` (the name is in the key); any future wrapper must do the same.
5. **The theme reaches components through CSS variables on a wrapper**, not on `<html>`, because the old provider writes its default theme onto `<html>` after hydration. The variable names are the old ones (`--tournament-primary` and so on), so moved view components keep their colours. Fonts given as named custom fonts (`local-oxanium-extrabold`) are not mapped yet (WP-08).
