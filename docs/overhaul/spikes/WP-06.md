# WP-06: the hosting trial, local part

Written on 2026-11-23 by Opus, on branch `wp/06-hosting-trial`. The owner has not yet switched on staging or allowed a deployment, so this is the half of WP-06 that runs on this machine: the helpers that M1 keeps (`src/platform/cache`, the forwarding rule), one server-rendered teams page on PostgreSQL, and the measuring scripts. Everything was measured against a local production build (`next start`) with the four imported tournaments in a local PGlite database. **The local numbers prove that the scripts work and that the page is cacheable; they are not the trial's result.** The trial's numbers come from a Vercel preview against the staging database, with the steps in "What remains" below.

The short version:

- `/<slug>/teams` of a tournament in the new database is rendered on the server from three cached statements, with the theme as CSS variables in the HTML and the team list in the first response. It is static per tournament (`Cache-Control: s-maxage=31536000`, `x-nextjs-cache: HIT` from the second request), and so is its client-navigation payload. An invalidation makes the next request render fresh data: locally about 40 ms after the call.
- Tournaments on the old site, the pages not moved yet, the old `/api/` routes and the old site's `/_next/` files are forwarded to the old site's address. All of it is config rewrites built when `PLATFORM_ROUTING=on`; without it a build has no rewrites, and the middleware runs on the same narrow set of paths as before (the one difference: `/platform/*` answers 404).
- The routing knows which slugs are new without asking the database, because it is given the short list of slugs that are still on the old site. Why that is enough is the next section but one.
- Found on the way, and important for M1: under `next start`, a middleware rewrite inside the app makes a page uncacheable and, next to config rewrites, does not reach it at all, so the routing is config rewrites only. An unknown slug answers 200 with the not-found page because of the root loading screen, and each such page is cached (an ISR write). The root layout still sends 44 kB of translations and a Firestore-reading provider with every page (the last two are WP-08's).

### The cache helpers (ADR-02, ADR-12)

`cachedQuery(fn, { name, tags, revalidate?, cacheNull? })` wraps a read in Next's data cache (`unstable_cache`). The key is the query's name and its arguments; the tags come from `tags.ts`, the only place a tag is spelled: `t:<tournamentId>` for everything of a tournament, `t:<tournamentId>:<kind>` for the kinds of ADR-12 (`core`, `teams`, `matches`, `standings`, `bracket`, `content`, `stats`, `fantasy`), and `slug:<slug>` for the slug lookup. Every tournament query carries the tournament-wide tag too, so one invalidation refreshes a whole tournament (after an import, or a theme change). `invalidate(tags)` is what a command or job will call. With `cacheNull: false` a `null` result is returned but not stored; the slug lookup uses it, so a made-up slug is looked up again on each request instead of becoming a permanent entry.

Two traps are closed in the helper. The data cache stores JSON, so a `Date` from the database would come back as a string on a hit and as a `Date` on the miss that filled it; a result that is not plain JSON is refused on the miss, every time. And Next keys an entry by the callback's source text plus the key parts; every callback made by the helper has the same source, so the name is part of the key. Pages that use these queries become static: Next attaches the queries' tags to the page, so an invalidation also drops the cached page and, on Vercel, the CDN copy.

### The page

`/platform/<slug>/teams` is the internal address; visitors use `/<slug>/teams`, and the internal one answers 404 from outside. It lives outside `src/app/[tournamentSlug]/` because that folder's layout is the old client layout with the loading screen and the Firestore reads; WP-08 turns that layout into a server component, and the page then moves into it. The page is `force-static` with an empty `generateStaticParams`: nothing is rendered at build time (a build reads no database, and `build-offline.mjs` still passes), each tournament is rendered on its first request and then served from the cache until a tag of its data is invalidated. `force-static` also stops the root layout's language cookie from making the page per-visitor; the language stays Polish until WP-08 takes it from the tournament. The slug `platform` is reserved (`src/lib/reserved-slugs.ts` and the copy in `firestore.rules`).

The team list is three statements whatever the number of teams (teams, current roster rows, group memberships with their stage), run in parallel, and assembled by `buildTeamList`: teams by group of the earliest stage, then name; players by position, then substitutes, then coaches; every team listed with its status, as on the old page. A database test asserts the three statements on an 18-team and an 8-team tournament.

### The forwarding rule (ADR-15)

Three variables, all read by `next.config.mjs` when the app is built and never at run time: changing one on a deployment does nothing until it is rebuilt, and a malformed value fails the build instead of every request.

| Variable | Meaning |
|---|---|
| `PLATFORM_ROUTING` | `on` builds the rules below. Anything else: no rewrite, no header, and the middleware does what it did before (the 410 on `/api/admin`, the `.rsc` strip) plus the 404 on `/platform/*` |
| `LEGACY_ORIGIN` | the old site's address. Unset: nothing is forwarded, and what the platform does not serve falls to the old pages that are still in this app (local runs) |
| `LEGACY_SLUGS` | comma-separated slugs still served by the old site; forwarded whole, even when they are also in the new database (a mirror) |

The middleware keeps its old, narrow matcher (`.rsc` paths, `/api/admin*`) plus `/platform` and `/platform/*`. It answers 410 on `/api/admin*` (with or without a file extension), 404 on `/platform/*` from outside (with routing on or off, so the internal page never runs without its rewrite), and strips `.rsc` when routing is off. With routing on it lets `.rsc` paths through to the rewrites; it learns which way from `PLATFORM_ROUTING_AT_BUILD`, which `next.config.mjs` inlines at build time, so it always agrees with the built rewrites.

The rewrites with routing on, `beforeFiles` (before the app's own pages), in this order:

1. `/<slug>/<moved page>`, with or without the `.rsc` suffix that client navigations carry through the community site, for a slug that is not on `LEGACY_SLUGS` and not `api`, `platform`, `prototype` or `_next`: to `/platform/<slug>/<page>`. These responses carry `x-platform-route: platform`.
2. With `LEGACY_ORIGIN`: `/`, and every path that is not under `/platform`, `/prototype`, `/_next` or `/api/platform` and is not a file (an image, a font, `robots.txt`, `sitemap.xml`): to the old site, with its query. That covers old-site tournaments, pages not moved yet, `/creator` and the old `/api/` routes. A client navigation keeps its `.rsc` suffix, which the old site's own middleware strips. Next applies `beforeFiles` rewrites one after another to the rewritten path, so a moved page, once it is `/platform/...`, is not caught here.
3. The `.rsc` suffix off every path left (the new app's own pages, and every page when nothing is forwarded).

And `fallback` (after every page, file and dynamic route, exactly like the community site's rule in front of us today): with `LEGACY_ORIGIN`, any path this build has nothing for goes to the old site. That is how the old site's `/_next/` files, which its pages load through us, are served. Static files never reach the middleware.

**Why rewrites and not the middleware.** Measured, not assumed, over several builds:

1. Under `next start`, a page reached through a middleware rewrite is rendered per request with `Cache-Control: private, no-cache, no-store`, because the route module re-reads the original URL and re-applies only the config's rewrites before it decides whether the page is static (`next/dist/build/templates/app-page.js`, `routeModule.match(pathname)`). Reached through a config rewrite, the same page is static (`x-nextjs-cache: MISS`, then `HIT`).
2. Once the config has `beforeFiles` rewrites, a middleware rewrite inside the app (the `.rsc` strip, to the moved page or to any other path) no longer reaches a page at all under `next start`: the request falls through to the `fallback` rewrite with its original path, so a client navigation through the community site was forwarded to the old site. Stripping the suffix with a config rewrite instead fixed it.
3. A middleware that decided the forwarding would have to run on every page and API request, because its matcher cannot depend on a variable. On the old hosting (Firebase's adapter) a route the middleware matches is served by Cloud Run and not copied to Hosting's CDN; today only `/icon.png` and `/robots.txt` are prerendered and both are outside the matcher, but any static page added to the old site later would have gone to Cloud Run, and every request would have cost a middleware call. An earlier commit of this branch did that; the review asked for the narrow matcher, which the rewrites allow.

On Vercel the router hands the function the rewritten path, so a middleware rewrite is expected to work there too, but the config rewrites work everywhere, including the fallback hosts of ADR-03. A related fact about today: on the old site's own hosting, a client navigation that came through the community site and was rewritten by the middleware is never served from a cache.

### How the routing knows which slugs are new

The WP says "a slug that is not in the new database is forwarded". Asking the database on every request is ruled out (latency at the edge, a database call per page view even for CDN hits). The options considered:

| Option | Cost per request | Staleness | Verdict |
|---|---|---|---|
| Query the database in the middleware | one round trip, at the edge | none | ruled out by the WP |
| The list of new slugs in an environment variable | none | a deployment per new tournament | fails at go-live step three, when organizers create tournaments themselves |
| Vercel Edge Config holding the new slugs | a read per request (counted; the free plan's allowance is far below 1,000,000 a month) | seconds | vendor-specific and metered on the free plan |
| The middleware fetches a cached list of new slugs from the app itself and keeps it in memory for a minute | none on a warm instance; a fetch per cold edge instance, which is a CDN request and a function call | up to a minute | adds CDN requests, and on a protected preview the fetch needs a bypass secret |
| **The list of old-site slugs in an environment variable, built into the rewrites (chosen)** | none | a deployment per go-live step | see below |

The choice rests on ADR-15: the old site is frozen for features, every new season is created on the new platform, and the old site's tournaments leave it one go-live step at a time. So the set the routing must know is the old site's, not the new platform's: today `pdl`, `pdl-s2`, `wiosenna`, `letnia`, and it only ever shrinks. Every tournament created on the new platform is served without any change to the setting, and each go-live step, which is a deliberate change with its own checks, removes one slug from the list in the same deployment. Nothing runs per request beyond Next's own route matching; the middleware did not grow (115 kB, most of it Sentry's edge SDK, WP-04's note).

What it does not do, and the cost of that: a slug that is in neither system is rendered by the new platform, whose page answers "not found", instead of being forwarded so that the old site answers "not found". A visitor sees the same thing. A tournament created on the old site after this setting was written would be missing from the list and would get the new platform's "not found" until it is added. The owner creates the old site's tournaments, so the rule for the go-live packages is: no new tournament on the old site, or add its slug to `LEGACY_SLUGS` the same day. If that ever becomes too fragile, the fallback is the cached-list option above, which needs the middleware on every page again.

The tests: `src/platform/routing/rules.test.ts` (every rule above run through Next's own router with `unstable_getResponseFromNextConfig`: moved pages with and without `.rsc`, forwards with their query and slashes, the new app's own paths and files kept, `pdl` on the list not catching `pdl-s2`, routing off, the settings), `src/middleware.test.ts` (the old behaviour, recorded before the change, plus the 404 on `/platform/*` with routing off and on, and the matcher, which skips pages).

## Found on the way

1. **Middleware rewrites inside the app do not work with static pages under `next start`** (above). The moved pages and the `.rsc` strip are config rewrites; with the rule on, the middleware only answers or forwards. To check on Vercel: that the same config rewrites give `x-vercel-cache: HIT` (step 5 below).
2. **An unknown slug answers 200 with the not-found page** (and `noindex`), not 404, for browsers and crawlers alike (checked with a Googlebot user agent): the root `src/app/loading.tsx` puts every page inside a Suspense boundary, so the status is sent before the page can call `notFound()`, and `notFound()` in `generateMetadata` does not help because the metadata streams too. **Cost:** the page is `force-static`, so each made-up slug a crawler tries (`/<anything>/teams`) becomes one cached page, an ISR write and stored output on Vercel, kept until that slug's tag is invalidated. The slug lookup behind it is no longer cached when it finds nothing (`cacheNull: false`), so the data cache does not grow too. WP-08 removes the root loading screen; a real 404 is then answered and the page cost is bounded. Until then, count the ISR writes during the staging run (Vercel's usage page) and watch them once the page is public.
3. **The root layout is heavy for every page.** Its `NextIntlClientProvider` carries all of `messages/pl.json` (44 kB) into each page's HTML and navigation payload, which is most of the 70 kB payload of a 12-team page; and its client providers start the Firestore SDK. Both are WP-08's (language from the tournament, providers seeded from the server).
4. **Next's data cache keys by the callback's source text.** Handled in `cachedQuery` (the name is in the key); any future wrapper must do the same.
5. **The theme reaches components through CSS variables on a wrapper**, not on `<html>`, because the old provider writes its default theme onto `<html>` after hydration. The variable names are the old ones (`--tournament-primary` and so on), so moved view components keep their colours. Fonts given as named custom fonts (`local-oxanium-extrabold`) are not mapped yet (WP-08).
